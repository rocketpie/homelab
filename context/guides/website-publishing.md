# Public Workload Publishing

This is the host contract for publishing a public workload image to a homelab
public gateway. It is the short version for a CI/CD owner. The same contract
ships on each host as `/root/website-publish.README.md`, generated by
`add_website`.

## Host contract

| Item | Value |
| --- | --- |
| Services | `website`, `lobby` |
| Image reference | `homelab/<service>:latest` |
| Required labels | `com.co3d.service=public`, `com.co3d.service.name=<service>` |
| Architecture | `linux/amd64` |
| Container ports | `website` 80, `lobby` 8080 |
| Artifact | `<service>.tar.zst` in `/opt/public/<service>/` |
| Optional integrity file | `<service>.tar.zst.sha256` |
| Deploy marker | `/opt/public/triggers/<service>.restart` |
| Deploy account | `website-deploy` |
| Deploy log | `/var/log/public-deploy.log` |

Caddy reaches each container by compose service name on the shared
`vpn-gateway-proxy` Docker network. Workloads publish no host ports.

## Lobby image requirements

The host runs `lobby` with `cap_drop: ALL`,
`no-new-privileges:true`, and `read_only:true`. The image must bind port 8080
as a non-root user.

The image owns ports and application defaults such as rate limits.
The host does not set them.

Do not use `setcap` or file capabilities in the image. A binary with
`cap_net_bind_service` fails to execute under `cap_drop: ALL`:

```text
exec /usr/local/bin/node: operation not permitted
```

Bind 8080 instead. Ports above 1024 do not need `CAP_NET_BIND_SERVICE`.

## CI build

The host never builds. CI builds the image and uploads a compressed
`docker save` archive.

```bash
docker buildx build --platform linux/amd64 --load \
  --label com.co3d.service=public \
  --label com.co3d.service.name=lobby \
  -t homelab/lobby:latest .

docker save homelab/lobby:latest | zstd -T0 -3 > lobby.tar.zst
sha256sum lobby.tar.zst > lobby.tar.zst.sha256
```

Replace `lobby` with `website` for the static site. The checksum file is
optional, but recommended.

## Upload and trigger

Use the private deploy key generated on the host:

```bash
rsync -az --delete --chmod=D755,F644 \
  -e 'ssh -i ~/.ssh/website-publish -o IdentitiesOnly=yes -o StrictHostKeyChecking=accept-new' \
  lobby.tar.zst lobby.tar.zst.sha256 \
  website-deploy@<host>:/opt/public/lobby/

ssh -i ~/.ssh/website-publish -o IdentitiesOnly=yes \
  website-deploy@<host> 'touch /opt/public/triggers/lobby.restart'
```

The marker filename is the compose service name. One marker deploys one
service. Always upload the archive before touching the marker.

To fetch the current private key after a playbook run:

```bash
ssh root@<host> 'cat /root/website-publish'
```

The key rotates by default on every playbook run. Store it in CI secrets only.

## What the host does

`/usr/local/sbin/public-deploy` runs from `/etc/cron.d/public-deploy` every
minute:

1. takes a lock so cron and a manual run cannot overlap
2. consumes the marker first, so a bad archive cannot hot-loop
3. verifies the optional checksum
4. checks that the service exists in the root-owned compose file
5. loads the archive with `docker load`
6. requires the loaded tag to be exactly `homelab/<service>:latest`
7. requires the image labels `public` and `<service>`
8. runs `docker compose up -d --no-deps --force-recreate <service>`
9. prunes unused public images and deletes the archive only after success

A rejected or failed deploy keeps the archive for inspection. The next publish
overwrites it. There is no image rollback on the host; roll back by
republishing the previous commit.

## Manual restart

Restart the currently loaded image without uploading anything:

```bash
cd /opt/public && sudo docker compose up -d --no-deps lobby
```

## Troubleshooting

On the host:

```bash
sudo tail -f /var/log/public-deploy.log
sudo docker compose -f /opt/public/docker-compose.yml ps
sudo ls -la /opt/public/lobby /opt/public/triggers
```

| Log line | Meaning |
| --- | --- |
| `skipping <service>: missing <archive>` | marker arrived before the archive |
| `skipping <service>: checksum mismatch` | uploaded archive does not match its `.sha256` |
| `skipping <service>: docker compose config failed: ...` | Docker or the compose file failed to parse; the error is included |
| `skipping <service>: not a service in ...` | marker name is not selected on this host; the service list is included |
| `skipping <service>: docker load failed` | archive is corrupt or not a `docker save` stream |
| `rejecting <service>: archive did not contain ...` | wrong image tag in the archive |
| `rejecting <service>: expected labels ...` | image labels missing or wrong |
| `<service> deploy complete` | load, restart, prune, and cleanup succeeded |

Caddy returns 502 until the first successful publish. That is expected on a
fresh host.

## Security boundary

The publish account has no sudo, is not in the `docker` group, and owns only the
artifact and trigger directories. It cannot read WireGuard keys directly:
`/opt/vpn-gateway/wg-easy` is root-owned and `wg-easy.db` is `0600`.

The host never executes publisher build instructions. The publish key still
controls the image that runs, so treat it as permission to run arbitrary code
in a container that is network-adjacent to wg-easy. Reading WireGuard keys
additionally requires a wg-easy vulnerability or a container escape. Keep the
key in CI secrets, never publish from an untrusted branch, and rotate it after
any suspicion.
